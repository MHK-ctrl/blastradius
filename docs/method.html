How the index is measured

Back to the numbers

SIMULATED. This run had no model API key, so every arm is a deterministic scripted policy driving a local fault-injection server, not an LLM. No number here is a model result.

What is counted

A task passes only if the server's final ledger equals the scenario's declared expected state, exactly — same number of rows, same fields. Anything else counts once as a duplicate-or-unauthorised write. The oracle is the ledger, never the guard's own journal.

Design

  • 45 scenarios across money, communication and records.
  • 5 trials per scenario per arm, each with a seed that selects the fault.
  • Two arms per scenario: guard off and guard on, same seeds, same faults.
  • Faults: timeout after the effect is applied, 429 before it, truncated body after it, stale read after it, schema drift after it.
  • Task-level retry policy: one retry per tool call, identical in both arms.
  • Metrics: failures per 1,000 tasks with a 95% Wilson interval; pass^1 and pass^k with k = 5, computed as C(c,k)/C(n,k) per scenario and averaged.

Impossible and do-nothing tasks

The set includes tasks that must be refused (a refund above the ceiling, an external send from an internal-only session) and tasks where no write is correct. A do-nothing agent passes the second kind, so those tasks are counted but they do not inflate the score; they exist to catch an agent that acts when it should not.

What this run does not show

It does not measure any LLM, any framework, or any real payment API. Model is scripted (SIMULATED). LangGraph and the OpenAI Agents SDK are listed on the front page as not run: no key was present and an unexercised adapter is worse than an empty row. Raw per-trial JSON, including every ledger row, is committed under index/results/ in the repository.
